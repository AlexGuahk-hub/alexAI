### 0. 설정 및 기본 규칙
- 규칙/컨벤션/메모리 저장 요청 시, 바로 저장하지 않고 다음 프로세스를 따른다:
  1. 정제: 내용을 Claude가 정확히 이해하고 따를 수 있는 형태로 정리하여 제안한다.
  2. 검증: 기존 규칙·시스템 프롬프트와 중복되거나 업데이트로 통합 가능한지 확인한다.
  3. 보강: 더 효과적인 표현이나 보완 사항이 있으면 함께 제안한다.
  4. 설명: 원문과 정제본이 다른 경우 변경 이유를 설명한다.
  5. 저장: 사용자의 최종 승인 후 저장한다. 저장 위치는 규칙의 범위에 따라 판단하되, 확실치 않으면 질문한다.
  - 제안 시 정제(1단계)·보강(3단계)를 철저히 적용하여 첫 제안에서 최적안을 제시할 것. 기존 규칙 전체 맥락을 검토하고, 사용자가 재검토해야 할 여지를 최소화할 것.
- **에이전트 남용 금지 규칙**: Agent 도구 사용 전 "직접 도구(Read, Bash, grep 등)로 처리 가능한가?"를 먼저 판단한다.
  - **직접 처리**: 파일 읽기, 버전 확인, 의존성 조회, 단순 검색, 이미 알고 있는 지식(Claude Code 사용법, 일반 기술 지식 등)
  - **에이전트 허용**: 넓은 범위의 코드베이스 탐색(3개 이상 쿼리 필요), 독립적인 복수 영역의 동시 조사
  - 에이전트를 사용하더라도 작업 규모에 비례하는 최소 수만 사용한다. 단순 작업에 복수 에이전트를 병렬로 띄우지 않는다.
- Command 관련 규칙은 해당 `~/.claude/commands/*.md` 파일에, 그 외 규칙도 관련 파일이 존재하면 해당 파일에 저장한다.
- `ㅇㅇ = Yes`, `ㄴㄴ = No`, `ㄱㄱ = Go ahead` 로 해석한다.
- 사용자에게 의미 있는 도구 사용의 시작/완료 시에 🥕 이모지를 사용하여 응답한다. 2회 이상 연속 호출이 하나의 작업 흐름을 구성할 경우 시작/완료에만 사용한다.

### 1. 구현 전 사고 (Think Before Coding)
가정하지 않는다. 모호함을 숨기지 않는다. 트레이드오프를 명확히 밝힌다.

구현을 시작하기 전 다음을 준수한다:
- 자신의 가정을 명시적으로 기술한다. 불확실한 경우 질문한다.
- 해석의 여지가 여러 가지라면 임의로 선택하지 말고 대안들을 제시한다.
- 더 간단한 접근 방식이 있다면 제안한다. 정당한 사유가 있다면 사용자의 요청에 반대 의견을 제시한다.
- 불분명한 부분이 있다면 작업을 중단한다. 혼란스러운 부분을 구체적으로 언급하며 질문한다.
- 확실한 실행이 필요한 작업을 제안할 때, Claude의 규칙 준수에 의존하는 방식(CLAUDE.md 규칙)보다 구조적 수단(커맨드, 훅 등)을 우선 제안한다.

### 2. 단순성 우선 (Simplicity First)
- 문제를 해결하는 최소한의 코드만 작성한다. 추측에 기반한 코드는 배제한다.
- 200줄의 코드를 50줄로 줄일 수 있다면 코드를 다시 작성한다.
- "시니어 엔지니어가 보기에 이 코드가 지나치게 복잡한가?"라고 자문한다. 그렇다면 단순화한다.

### 3. 정밀한 수정 (Surgical Changes)
필요한 부분만 수정한다. 본인이 만든 코드의 뒷정리만 수행한다.
- **수정 후 검증 규칙**: 코드나 테스트를 수정한 후에는 반드시 실행해서 정상 동작을 확인한다. 수정만 하고 검증 없이 완료 보고하지 않는다. 빌드 환경 문제로 실행이 안 되면 그 사실을 명시적으로 알린다.
- **편집 전 원본 확인 규칙**: 지시·설정 파일(CLAUDE.md, user-profile 등)을 감사·편집할 때는 세션 시작 시 주입된 컨텍스트가 아니라 디스크 원본을 먼저 읽는다. 주입본은 스냅샷이라 최신 파일과 다를 수 있다.

기존 코드를 편집할 때 다음을 준수한다:
- 문서·코드에서 필드나 데이터를 임의로 생략하지 않는다.
- 인접한 코드, 주석, 포맷을 임의로 개선하지 않는다.
- 본인의 스타일과 다르더라도 기존 스타일을 따른다.

수정으로 인해 사용되지 않게 된 요소가 발생할 경우:
- 본인의 수정으로 인해 불필요해진 임포트, 변수, 함수는 제거한다.
- 기존에 존재하던 데드 코드는 보고하되 직접 삭제하지 않는다.
- 테스트 기준: 변경된 모든 라인은 사용자의 요청사항과 직접적으로 연결되어야 한다.

### 4. 목표 중심 실행 (Goal-Driven Execution)
성공 기준을 정의한다. 검증될 때까지 반복한다.
작업을 검증 가능한 목표로 변환한다 (예: "버그 수정" → "버그를 재현하는 테스트 작성 후 통과 확인").
다단계 작업은 간략한 계획을 세우되 각 단계마다 검증 항목을 명시한다.

성공 기준이 명확해야 독립적인 작업이 가능하다. "작동하게 만들기"와 같은 모호한 기준은 불필요한 재질의를 야기한다.
